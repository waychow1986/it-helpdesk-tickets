# 内部 IT 工单系统 V2 产品规格

## 产品目标与边界

本规格把已批准 Intent（INT-001～INT-016）转化为 V2 的技术无关、可观察、可验收产品行为。V2 在已上线的 V1 之上增量交付；除本规格明确新增或修改的行为外，V1 已确定的业务决定和产品行为保持不变（Intent「业务约束与优先级」"沿用 V1 已确定的业务决定"、INT-014）。

- **目标**：
  - 每张工单都有按紧急程度自动给出的期望解决时间，员工和 IT 同事在列表和详情中能直接看到，并能一眼识别超时未解决的工单（INT-001、INT-005～INT-008）。
  - 管理员可以停用和重新启用账号；停用账号不能登录、不再可被分派，其历史工单与沟通记录照常保留和显示；系统始终至少保留一个可用管理员（INT-002、INT-009～INT-012、INT-016）。
  - 周报表新增"本周超时解决的工单数量"（INT-003、INT-013）。
  - 在 V1 线上数据上直接升级，既有数据保持不变并按原权限可查看，升级可安全重复执行（INT-004、INT-014、INT-015）。
- **边界内**：期望解决时间的计算、显示与超时标识；V1 既有工单补上期望解决时间；账号停用与重新启用及其对登录、分派、历史显示的影响；最后一个可用管理员保护；周报表新增一项；从 V1 原地升级与重复升级。
- **边界外**：超时外部通知 / 提醒 / 自动升级；按工作日或节假日日历计算期望解决时间；手工设置或修改期望解决时间、按类别等条件设定不同时限；删除账号、员工自助停用；改变 V1 周报表四项口径；附件、对接公司现有登录系统、自动分派、移动端原生应用等 V1 范围外能力（Intent「范围外」）。

## 参与者与权限

| 参与者 | 身份 | V2 新增或变化的允许操作 | 不允许的操作 |
|---|---|---|---|
| 员工 | 员工 | 在本人工单列表和详情中看到期望解决时间与超时标识 | 停用 / 启用任何账号；查看他人工单；其余同 V1 |
| IT 同事 | IT 同事 | 在全部工单列表和详情中看到期望解决时间与超时标识；分派对象仅限未停用的 IT 同事 | 停用 / 启用任何账号；其余同 V1 |
| 管理员 | 管理员 | 停用账号、重新启用已停用账号；在账号列表中看到每个账号的启用 / 停用状态；查看含新增项的周报表 | 停用后会使系统不再有可用管理员的停用操作（含停用自己）；其余同 V1 |
| IT 主管 | 使用管理员身份 | 与管理员相同（沿用 V1：报表查看权限由管理员角色承担） | 同管理员 |
| 已停用账号的持有人 | 原身份保持不变，但处于停用状态 | 无（不能登录，不能使用任何功能） | 登录或继续使用系统任何功能 |
| 未登录访问者 | 无 | 同 V1 | 同 V1 |

权限依据：INT-001、INT-006、INT-009、INT-010、INT-016；Intent 业务约束"沿用 V1 已确定的业务决定"（身份分为员工、IT 同事、管理员三种，IT 主管通过管理员角色查看报表）；宪章「安全与隐私」"执行 least privilege"。

## 用户故事

### US-001 查看工单期望解决时间（P1）

作为员工或 IT 同事，我希望在工单列表和详情中看到每张工单按紧急程度自动给出的期望解决时间，以便判断工单应在何时前解决。（INT-001、INT-005、INT-006）

### US-002 识别超时未解决的工单（P1）

作为员工或 IT 同事，我希望超过期望解决时间仍未解决的工单在列表和详情中被醒目标出，以便及时处理或跟进拖延的工单。（INT-001、INT-007）

### US-003 管理员停用和重新启用账号（P1）

作为管理员，我希望停用离开或不再需要使用系统的人员账号，并能在需要时重新启用，以便停用账号无法登录、不再被分派工单。（INT-002、INT-009、INT-010、INT-011、INT-016）

### US-004 停用账号的历史记录照常保留（P1）

作为员工、IT 同事或管理员，我希望被停用账号历史上提交或处理过的工单、沟通记录照常保留和显示，以便业务记录和统计不因人员变动而缺失。（INT-002、INT-012）

### US-005 周报表查看本周超时解决数（P1）

作为使用管理员身份的 IT 主管，我希望在周报表中看到本周超时解决的工单数量，以便衡量处理时效。（INT-003、INT-013）

### US-006 从 V1 平滑升级（P1）

作为系统的所有使用者，我希望系统在 V1 线上数据上直接升级到 V2 后，全部既有数据保持不变并按原权限可查看，既有工单也补上期望解决时间，且升级可以安全地重复执行，以便业务记录和统计依据不受升级影响。（INT-004、INT-008、INT-014、INT-015）

## 功能需求

**期望解决时间与超时标识**

- **FR-001**：每张工单的期望解决时间 = 提交时间 + 按紧急程度确定的时长：高 = 4 小时，中 = 24 小时，低 = 72 小时；按自然时间计算，不扣除夜间、周末和节假日（INT-005、BQ-001 人工答案 A）。新工单在提交成功时即获得期望解决时间。
- **FR-002**：期望解决时间只由紧急程度和提交时间决定；由于二者提交后不可修改（V1），期望解决时间一经确定不再改变，状态修改、认领、分派、补充说明、回复、类别改名或移除、账号停用或启用均不改变它。系统不提供任何人手工设置或修改期望解决时间的入口（Intent「范围外」）。
- **FR-003**：员工的"我的工单"列表、IT 同事的全部工单列表，以及工单详情，均对每张工单（不限状态）显示其期望解决时间，显示精确到日期和时刻（INT-006）。搜索和筛选结果列表同样显示（closure，见追踪矩阵）。
- **FR-004**：超时未解决 = 工单当前状态为"待处理"或"处理中"，且当前时刻晚于其期望解决时间；当前时刻恰好等于期望解决时间时不算超时（INT-007）。
- **FR-005**：超时未解决的工单在 FR-003 所述的列表和工单详情中以醒目、可与未超时工单明确区分的标识标出；未超时的未解决工单、以及状态为"已解决"或"已关闭"的工单（无论其解决时刻是否晚于期望解决时间）不显示该标识（INT-007）。
- **FR-006**：超时标识按查看时的工单状态和当时时刻判定：已解决或已关闭的工单被改回"待处理"或"处理中"时，若当时已晚于期望解决时间即显示超时标识；超时未解决的工单被改为"已解决"或"已关闭"后不再显示超时标识（INT-007）。

**账号停用与重新启用**

- **FR-007**：管理员可以停用任一处于启用状态的账号（员工、IT 同事或管理员），也可以重新启用任一已停用账号；停用和重新启用都不改变账号的登录名、登录凭据、显示姓名和身份（INT-009）。
- **FR-008**：管理员的账号列表对每个账号显示其当前为"启用"或"停用"（closure，见追踪矩阵）。V1 已有账号和新创建的账号默认处于启用状态。
- **FR-009**：已停用账号不能登录：使用其登录名和正确凭据登录时被拒绝并不进入系统，提示与 V1 登录失败提示一致（INT-010）。账号被停用时若其持有人仍处于已登录状态，其下一次操作被拒绝并被引导至登录入口，之后无法再使用任何功能（closure，见追踪矩阵）。
- **FR-010**：重新启用后，该账号可用原登录名和原凭据重新登录，按其原身份获得与 V1 相同的能力（INT-009）。
- **FR-011**：可分派对象 = 身份为 IT 同事且处于启用状态的账号。已停用的 IT 同事不出现在分派对象中；分派给在提交分派时已被停用的 IT 同事的操作被拒绝，工单不变。重新启用的 IT 同事重新出现在分派对象中（INT-011）。
- **FR-012**：停用 IT 同事时，其名下尚未解决的工单不被自动改动，仍显示其为处理人，直到其他 IT 同事重新认领或分派（INT-012、BQ-003 人工答案 A）。
- **FR-013**：被停用账号历史上提交或处理过的工单、沟通记录（补充说明与回复）和处理记录照常保留，并对有权查看该工单的用户照常显示，包括提交人姓名、处理人姓名、作者姓名与身份；这些工单在列表、详情、搜索和筛选中的出现方式与停用前相同（包括按处理人筛选时，处理人为已停用账号的工单仍可被筛出）；周报表中该账号相关的统计照常计入（INT-012）。
- **FR-014**：系统必须始终至少保留一个处于启用状态的管理员账号。当一次停用操作执行后将不再有启用状态的管理员时（包括管理员停用自己），系统拒绝该操作、账号状态不变，并提示原因"系统必须至少保留一个可用的管理员"或同义说明。在仍有其他启用状态管理员的情况下，管理员可以停用其他管理员或自己；停用自己后按 FR-009 处理（INT-016）。
- **FR-015**：只有管理员可以停用或重新启用账号；员工和 IT 同事看不到这些入口，直接发起这些操作时被拒绝且账号状态不变（宪章「安全与隐私」"执行 least privilege"；INT-009）。
- **FR-016**：停用的账号仍占用其登录名；创建新账号时使用与已停用账号相同的登录名，按 V1 登录名唯一规则被拒绝（closure，见追踪矩阵）。

**周报表**

- **FR-017**：周报表在 V1 四项统计之外新增第五项"本周超时解决的工单数量"= 首次被标记为"已解决"的时刻落在当前自然周内、且该首次已解决时刻晚于其期望解决时间的工单数量（INT-013、BQ-002 人工答案 A）。首次已解决时刻恰好等于期望解决时间的工单不计入；首次已解决时刻不在本周内的工单（包括本周再次被标记为已解决的工单）不计入；工单首次解决后又被改为其他状态，不影响其是否计入；状态被改为"已关闭"但从未被标记为"已解决"的工单不计入。本周没有可计入工单时显示 0。
- **FR-018**：V1 周报表原有四项（每个类别的工单数量、平均处理时长、每位 IT 同事处理量、超过 3 天未解决的工单数）的内容和统计口径保持不变；报表访问权限保持不变（仅管理员）（Intent「范围外」"改变 V1 已有的周报表四项统计口径"、Intent 业务约束）。

**从 V1 升级**

- **FR-019**：V2 在 V1 线上数据上直接升级。升级后，V1 的全部账号（登录名、凭据、显示姓名、身份）、类别（含已移除类别及其与历史工单的关联）、工单（编号、标题、描述、类别、紧急程度、提交人、提交时间、状态、处理人、首次已解决时刻）、沟通记录和处理记录保持不变，且各身份按 V1 原权限可以查看；除为既有工单补上期望解决时间外，不新增、丢失或改变任何已有数据（INT-014）。
- **FR-020**：升级为每张 V1 既有工单按其各自的紧急程度和提交时间、以 FR-001 相同口径补上期望解决时间；补上后按 FR-003～FR-006 显示和标识，并按 FR-017 计入周报表（INT-008、INT-013）。
- **FR-021**：升级后，V1 的全部账号均处于启用状态，可用原登录名和原凭据登录（closure，见追踪矩阵）；V1 中已完成的"设置初始管理员"流程在升级后仍不可用（INT-014，沿用 V1 行为）。
- **FR-022**：升级后，周报表 V1 原有四项的结果与升级前对同一数据的结果一致（"超过 3 天未解决的工单数"随时间自然变化除外）（INT-014）。
- **FR-023**：升级过程可以安全地重复执行：对已完成升级的系统再次执行升级，不新增、丢失或改变任何数据——包括不产生重复记录、不改变已有工单的期望解决时间、不改变升级后产生的新数据（新工单、新沟通与处理记录、账号的停用 / 启用状态）。升级在中途中断后再次执行，最终结果与一次成功执行的结果相同（INT-015）。

## 产品质量要求

- **NFR-001**（INT-004、INT-014、INT-015）：升级数据完整性——从 V1 升级以及任何一次重复执行升级，都不得导致已有数据丢失或被改变（为既有工单补上期望解决时间除外）；行为见 FR-019～FR-023。

除上述一项外，当前没有获批准的额外质量要求。

## 领域术语

| 术语 | 定义 |
|---|---|
| 期望解决时间 | 工单应被解决的时刻 = 提交时间 + 按紧急程度确定的时长（高 4 小时、中 24 小时、低 72 小时，自然时间） |
| 未解决 | 工单状态为"待处理"或"处理中"（沿用 V1） |
| 超时未解决 | 未解决且当前时刻晚于期望解决时间 |
| 超时标识 | 在工单列表和详情中把超时未解决工单与其他工单明确区分的醒目标记 |
| 首次已解决时刻 | 工单第一次被修改为"已解决"状态的时刻（沿用 V1） |
| 超时解决 | 首次已解决时刻晚于期望解决时间 |
| 本周超时解决的工单数量 | 首次已解决时刻落在当前自然周内且属于超时解决的工单数量 |
| 自然周 | 沿用 V1：周一 00:00 至周日 24:00 的连续 7 天 |
| 启用 / 停用 | 账号的使用状态；启用的账号可登录，停用的账号不能登录、不可被分派，数据保留 |
| 可用管理员 | 身份为管理员且处于启用状态的账号 |
| 可分派对象 | 身份为 IT 同事且处于启用状态的账号 |
| 升级 | 在 V1 线上数据上直接把系统更新为 V2 的过程 |
| 重复执行升级 | 对已完成或中途中断的升级再次执行升级 |

## 前置条件与触发条件

- **查看期望解决时间与超时标识**：用户已以员工或 IT 同事身份登录且账号处于启用状态；员工只针对本人工单（沿用 V1 权限）。
- **停用 / 启用账号**：用户已以管理员身份登录且账号处于启用状态；目标账号存在。停用时目标账号处于启用状态；重新启用时目标账号处于停用状态。
- **分派**：用户为启用状态的 IT 同事；存在另一位启用状态的 IT 同事。
- **周报表**：用户已以启用状态的管理员身份登录；报表在每次打开时按当时数据计算（沿用 V1）。
- **升级**：存在已上线、含有 V1 数据的系统。
- **触发**：员工提交工单（产生期望解决时间）；用户打开工单列表、搜索 / 筛选结果或详情（按当时时刻判定超时标识）；IT 同事修改状态（可能出现或消除超时标识）；管理员停用 / 启用账号；管理员打开周报表；执行升级或重复执行升级。

## 行为模型

### US-001 查看期望解决时间

- **正常**：员工提交紧急程度为高 / 中 / 低的工单 → 提交成功后，"我的工单"列表和详情显示期望解决时间分别为提交时间 + 4 / 24 / 72 小时；IT 同事在全部工单列表和详情中看到相同的期望解决时间（FR-001、FR-003；AC-001）。
- **替代**：工单经历认领、分派、状态修改、回复、补充说明后 → 期望解决时间不变（FR-002；AC-002）。
- **边界**：已解决和已关闭的工单仍显示期望解决时间；跨夜、跨周末的期望解决时间按自然时间计算，不顺延（FR-001、FR-003；AC-001）。
- **边界**：搜索和筛选结果列表中同样显示期望解决时间（FR-003；AC-001）。

### US-002 识别超时未解决工单

- **正常**：待处理或处理中、且当前时刻已晚于期望解决时间的工单 → 列表和详情显示超时标识（FR-004、FR-005；AC-003）。
- **替代**：未到期望解决时间的未解决工单 → 不显示超时标识；已解决 / 已关闭的工单即使解决晚于期望解决时间 → 不显示超时标识（FR-005；AC-003）。
- **替代**：超时的工单被改为已解决 → 标识消失；已解决的工单在期望解决时间之后被改回待处理 → 显示超时标识（FR-006；AC-004）。
- **边界**：当前时刻恰好等于期望解决时间 → 不算超时（FR-004；AC-003）。

### US-003 停用和重新启用账号

- **正常**：管理员停用一个启用状态的员工账号 → 账号列表显示"停用"；该员工用正确凭据登录被拒（FR-007、FR-008、FR-009；AC-005、AC-006）。
- **正常**：管理员重新启用该账号 → 账号列表显示"启用"；该员工用原凭据登录成功，能力与停用前相同（FR-007、FR-010；AC-005、AC-006）。
- **替代**：被停用时该账号正处于登录状态 → 其下一次操作被拒绝并被引导至登录入口（FR-009；AC-006）。
- **正常**：管理员停用一位 IT 同事 → 其不再出现在分派对象中；其名下未解决工单仍显示其为处理人（FR-011、FR-012；AC-007、AC-008）。
- **错误**：IT 同事在分派对象列表加载后、提交分派前，目标同事被停用 → 分派被拒绝，工单不变（FR-011；AC-007）。
- **错误**：管理员尝试停用唯一的可用管理员（含自己）→ 被拒绝并提示原因，账号状态不变（FR-014；AC-009）。
- **替代**：存在另一位可用管理员时，管理员停用自己 → 成功，其下一次操作被拒绝并被引导至登录入口；另一位管理员仍可登录并管理（FR-014、FR-009；AC-009）。
- **错误**：员工或 IT 同事直接发起停用 / 启用操作 → 被拒绝，账号状态不变（FR-015；AC-010）。
- **边界**：用已停用账号的登录名创建新账号 → 按登录名重复被拒（FR-016；AC-005）。

### US-004 停用账号的历史记录照常显示

- **正常**：停用一名提交过工单并写过补充说明的员工 → IT 同事仍能在列表、搜索、筛选和详情中看到这些工单，提交人姓名、补充说明的作者姓名与内容照常显示（FR-013；AC-008）。
- **正常**：停用一名处理过工单并回复过的 IT 同事 → 这些工单仍显示其为处理人，回复与处理记录照常显示；按处理人筛选该同事仍能筛出其工单；周报表中其处理量照常计入（FR-012、FR-013；AC-008）。
- **恢复**：其他 IT 同事认领或分派原由停用同事处理的未解决工单 → 处理人变更，处理记录记录前后值（沿用 V1）（FR-012；AC-008）。

### US-005 周报表本周超时解决数

- **正常**：管理员打开周报表 → 在 V1 四项之外看到"本周超时解决的工单数量"，其值等于本周首次被标记为已解决且首次已解决时刻晚于期望解决时间的工单数（FR-017；AC-011）。
- **边界**：首次已解决时刻在本周但未晚于期望解决时间 → 不计入；首次已解决时刻在上周、本周再次标记已解决 → 不计入；只被改为已关闭从未标记已解决 → 不计入；本周无可计入工单 → 显示 0（FR-017；AC-011）。
- **边界**：V1 四项结果和口径不变（FR-018；AC-012）。
- **错误**：员工或 IT 同事访问报表 → 拒绝（沿用 V1）（FR-018；AC-012）。

### US-006 从 V1 升级与重复升级

- **正常**：含 V1 数据的系统升级到 V2 → 各身份用原凭据登录，按原权限看到与升级前完全相同的账号、类别、工单、沟通记录和处理记录；每张既有工单显示按其紧急程度和提交时间计算的期望解决时间，超时未解决的既有工单显示超时标识；周报表 V1 四项结果与升级前一致（FR-019～FR-022、NFR-001；AC-013、AC-014）。
- **替代**：对已升级系统再次执行升级 → 所有数据（含升级后新产生的工单、记录和账号停用状态）不变、无重复（FR-023；AC-015）。
- **恢复**：升级中途中断 → 再次执行升级，最终结果与一次成功升级相同（FR-023；AC-016）。

## 业务状态、业务数据规则与不变量

**工单状态**：沿用 V1 的待处理、处理中、已解决、已关闭四种，状态间可任意修改。超时未解决不是一种新的工单状态，而是由状态、期望解决时间和当前时刻派生出的显示标识。

**账号使用状态**：启用、停用两种。启用 → 停用（管理员停用，受 INV-004 约束）；停用 → 启用（管理员重新启用）。账号身份与使用状态互相独立。

**不变量**

- **INV-001**：每张工单恰有一个期望解决时间，等于提交时间 + 其紧急程度对应的时长（高 4 小时、中 24 小时、低 72 小时）；一经确定不再改变。
- **INV-002**：工单显示超时标识，当且仅当其状态为待处理或处理中且当前时刻晚于期望解决时间。
- **INV-003**：每个账号在任一时刻恰处于启用或停用之一；停用状态的账号不能登录、不是可分派对象。
- **INV-004**：任一时刻至少存在一个可用管理员（身份为管理员且处于启用状态）。
- **INV-005**：停用和重新启用不改变账号的登录名、凭据、姓名、身份，也不改变任何工单、沟通记录或处理记录。
- **INV-006**：升级与重复执行升级不新增、丢失或改变任何已有数据，唯一例外是为尚无期望解决时间的既有工单补上按 INV-001 计算的期望解决时间。
- **INV-007**：V1 规格中的既有不变量（工单状态唯一、员工只见本人工单、记录只追加、首次已解决时刻不变、登录名唯一等）继续成立。

**业务数据规则**

- 期望解决时间、超时判定和周报表统计均使用与 V1 相同的公司统一本地时间（沿用 V1）。
- 账号停用 / 启用没有附加的必填信息（见假设 A-003）。

## 错误与恢复行为

| 情形 | 系统行为 | 恢复方式 |
|---|---|---|
| 已停用账号登录 | 拒绝登录，提示与 V1 登录失败一致，不进入系统 | 联系管理员重新启用 |
| 账号被停用时仍处于登录状态 | 下一次操作被拒绝并被引导至登录入口 | 联系管理员重新启用 |
| 分派给已停用的 IT 同事 | 拒绝分派，工单不变 | 刷新后从当前可分派对象中选择 |
| 停用最后一个可用管理员（含停用自己） | 拒绝，账号状态不变，提示必须至少保留一个可用管理员 | 先创建或启用另一个管理员账号，再执行停用 |
| 非管理员发起停用 / 启用 | 拒绝并提示无权限，账号状态不变 | 无需恢复 |
| 停用已停用的账号 / 启用已启用的账号 | 不产生变更，账号状态保持不变 | 无需恢复 |
| 用已停用账号的登录名创建账号 | 按登录名重复拒绝创建 | 使用其他登录名，或重新启用原账号 |
| 停用的 IT 同事名下有未解决工单 | 工单不自动改动，仍显示原处理人 | 其他 IT 同事重新认领或分派 |
| 升级中途中断 | 不得以不完整状态被视为升级完成 | 再次执行升级，结果与一次成功升级相同 |
| 对已升级系统再次执行升级 | 数据不变、不产生重复 | 无需恢复 |
| 停用 / 启用操作因任何原因未成功保存 | 明确提示失败，不显示为成功，账号状态保持操作前状态（沿用 V1） | 用户重试 |

## 安全、隐私与可访问性行为

- **访问控制**（宪章「安全与隐私」"执行 least privilege"；INT-009、INT-010、INT-016）：只有可用管理员能停用和重新启用账号（FR-015）；停用账号不能登录，已登录的停用账号在下一次操作时失去访问（FR-009）；期望解决时间与超时标识只在用户原本有权查看的工单上显示，员工仍只能看到本人工单（沿用 V1）。
- **输入验证**（宪章「安全与隐私」"验证输入"）：停用 / 启用的目标账号、分派对象的启用状态、最后一个可用管理员约束均被校验（FR-011、FR-014、FR-015）。
- **凭据**（宪章「安全与隐私」"凭据保留在服务端""绝不记录 secret"）：停用和重新启用不显示、不回显账号凭据；升级不改变账号凭据（FR-007、FR-019）。
- 可访问性：当前没有获批准的额外要求；超时标识只要求"醒目、可与未超时工单明确区分"（FR-005），不设正式可访问性等级。

## 性能、可靠性与其他质量边界

- 可靠性：仅限 NFR-001 升级数据完整性与可重复执行（FR-019～FR-023）。
- 性能、容量、可用率、升级时长或停机时长：当前没有获批准的额外要求。

## 成功标准

- **SC-001**：每张工单（含 V1 既有工单）在列表和详情中都显示按高 4 小时 / 中 24 小时 / 低 72 小时自提交时刻计算的期望解决时间，员工和 IT 同事能直接分辨出全部且仅有的超时未解决工单（INT-001）。
- **SC-002**：被停用的账号无法登录、不出现在分派对象中，重新启用后恢复原能力；其历史工单与沟通记录完整照常显示；系统任何时刻都至少保留一个可用管理员（INT-002、INT-016）。
- **SC-003**：周报表"本周超时解决的工单数量"与按 BQ-002 人工答案口径对同一数据手工计算的结果一致，V1 原有四项结果不变（INT-003）。
- **SC-004**：从 V1 升级及重复执行升级后，全部既有数据完整、不变并按原权限可查看，仅既有工单新增了正确的期望解决时间（INT-004）。

## 验收场景

### IQA-001 新工单按紧急程度获得期望解决时间

- **追踪：** INT-001、INT-005、INT-006、BQ-001 人工答案 A / US-001 / FR-001、FR-002、FR-003 / AC-001、AC-002
- **前置条件：** V2 候选环境中有启用状态的合成员工账号 E1、IT 同事账号 T1、T2，至少一个有效类别。
- **操作：** 1）E1 分别以高、中、低紧急程度各提交一张工单，记录各自的提交时间。2）E1 查看"我的工单"列表和三张工单详情；T1 查看全部工单列表和三张工单详情；E1、T1 各用一个能命中这些工单的关键词搜索并按状态筛选。3）T1 对其中一张工单依次认领、分派给 T2、改为处理中、改为已解决、改为已关闭、回复；E1 补充说明。4）再次查看该工单列表项和详情。
- **预期结果：** 三张工单的期望解决时间分别等于提交时间 + 4 小时、+ 24 小时、+ 72 小时（自然时间，不顺延），在 E1 和 T1 的列表、搜索 / 筛选结果和详情中一致显示，精确到日期和时刻；步骤 3 的各项操作后期望解决时间不变，且已解决 / 已关闭状态下仍显示期望解决时间；页面上不存在设置或修改期望解决时间的入口。任一不符即失败。
- **必需证据：** 各视图截图或录屏，标明提交时间与期望解决时间；步骤 3 前后对比截图。

### IQA-002 超时未解决工单醒目标出

- **追踪：** INT-001、INT-007 / US-002 / FR-004、FR-005、FR-006 / AC-003、AC-004
- **前置条件：** 合成员工 E1 名下有以下合成工单（提交时间早于当前时刻，由测试环境的数据准备方式构造）：A 高紧急、提交于 5 小时前、待处理；B 中紧急、提交于 25 小时前、处理中；C 低紧急、提交于 10 小时前、待处理；D 高紧急、提交于 6 小时前、已解决；E 中紧急、提交于 30 小时前、已关闭；另有 IT 同事 T1。

- **必需证据：** 步骤 1 与步骤 3 的列表和详情截图，标注每张工单的状态、期望解决时间和查看时刻。

### IQA-003 管理员停用与重新启用账号

- **追踪：** INT-002、INT-009、INT-010 / US-003 / FR-007、FR-008、FR-009、FR-010、FR-016 / AC-005、AC-006

- **追踪：** INT-003、INT-013、BQ-002 人工答案 A / US-005 / FR-017、FR-018 / AC-011、AC-012
- **前置条件：** 合成工单（提交时间和首次已解决时刻由测试环境的数据准备方式构造）：P1 高紧急、首次已解决于本周且晚于期望解决时间；P2 中紧急、首次已解决于本周且早于期望解决时间；P3 低紧急、首次已解决于上周且晚于期望解决时间、本周被改回处理中后再次标记为已解决；P4 高紧急、首次已解决于本周且晚于期望解决时间、之后被改回待处理；P5 高紧急、提交于 5 小时前、待处理，由 IT 同事在测试中把它直接改为已关闭；P6 高紧急、提交于 5 小时前、待处理，由 IT 同事在测试中把它标记为已解决。记录 QA 按 FR-017 与 V1 口径对这些数据手工计算的期望值。
- **操作：** 1）IT 同事执行 P5、P6 的状态修改。2）管理员打开周报表。3）员工、IT 同事分别尝试访问周报表。
- **预期结果：** 报表在 V1 四项之外显示"本周超时解决的工单数量"，其值等于 P1、P4、P6 三张（加上环境中其他本周首次超时解决的工单，按同一口径计算）；P2、P3、P5 不计入；V1 原有四项按 V1 口径计算的结果与手工期望值一致；员工、IT 同事访问报表被拒绝。任一不符即失败。
- **必需证据：** 报表截图、合成数据清单与手工计算过程。

### IQA-009 从 V1 升级后数据保持不变并补上期望解决时间

- **追踪：** INT-004、INT-008、INT-014 / US-006 / FR-019、FR-020、FR-021、FR-022、NFR-001 / AC-013、AC-014
- **前置条件：** 测试环境先部署 V1，并在 V1 中准备合成数据集，覆盖：员工、IT 同事、管理员三种身份账号；被取消 IT 同事身份的账号；有效类别与已移除类别、改过名的类别；三种紧急程度、四种状态、有 / 无处理人的工单，包括提交时间已超过其期望解决时间的未解决工单和未超过的未解决工单；含补充说明、回复和认领 / 分派 / 状态修改记录的工单；本周首次已解决的工单。升级前以各身份登录，记录账号列表、类别、各身份可见的工单列表与详情（含沟通与处理记录）、周报表四项结果，作为升级前快照。
- **操作：** 1）将该环境升级为 V2 候选版本。2）以升级前的各账号原凭据登录，逐项对比升级前快照；检查每张既有工单的期望解决时间和超时标识；员工尝试访问他人工单；打开周报表；访问"设置初始管理员"流程。
- **预期结果：** 所有账号可用原凭据登录且在账号列表中均显示为"启用"；账号、类别、工单、沟通记录、处理记录与升级前快照完全一致，各身份可见范围与 V1 原权限一致（员工仍只见本人工单）；每张既有工单的期望解决时间 = 其提交时间 + 4 / 24 / 72 小时（按紧急程度）；超时未解决的既有工单显示超时标识，其余不显示；周报表 V1 四项与升级前一致（"超过 3 天未解决"仅随时间自然变化），并显示第五项且其值符合 FR-017；"设置初始管理员"流程不可用。任一数据缺失或改变即失败。
- **必需证据：** 升级前快照与升级后对应截图或导出的逐项对比记录；期望解决时间核对表。

### IQA-010 重复执行升级不改变数据

- **追踪：** INT-004、INT-015 / US-006 / FR-023、NFR-001 / AC-015
- **前置条件：** IQA-009 完成后的已升级环境；在 V2 中新增数据：提交一张新工单并回复、停用一个合成账号、将一张既有工单改为已解决。记录此时的账号列表（含启用 / 停用状态）、工单列表与详情（含期望解决时间、超时标识、沟通与处理记录）和周报表，作为快照。
- **操作：** 1）对该环境再次执行升级到同一 V2 候选版本。2）以各身份登录，逐项对比快照。
- **预期结果：** 全部数据与快照一致：无重复的账号、类别、工单或记录；已有工单的期望解决时间不变；停用账号仍为停用且仍不能登录；V2 中新增的工单和记录完整保留；周报表结果一致（随时间自然变化的项除外）。任一不符即失败。
- **必需证据：** 再次升级前后的快照与逐项对比记录。

## 验收标准

- **AC-001**：新工单提交后，其期望解决时间等于提交时间 + 4 小时（高）/ 24 小时（中）/ 72 小时（低），自然时间不顺延；员工本人工单列表、IT 同事全部工单列表、搜索 / 筛选结果和工单详情对任何状态的工单均显示期望解决时间，精确到日期和时刻。
- **AC-002**：工单的期望解决时间在认领、分派、状态修改、回复、补充说明后保持不变，系统中不存在手工设置或修改期望解决时间的入口。
- **AC-003**：状态为待处理或处理中且当前时刻晚于期望解决时间的工单，在列表和详情中显示醒目、可区分的超时标识；未到期（含恰好到期）的未解决工单和已解决 / 已关闭的工单不显示该标识。
- **AC-004**：超时工单改为已解决或已关闭后标识消失；已解决或已关闭的工单在期望解决时间之后被改回待处理或处理中时显示超时标识。
- **AC-005**：管理员可以停用和重新启用账号，账号列表显示每个账号的启用 / 停用状态；停用与启用不改变账号的登录名、姓名和身份；已停用账号的登录名不能被新账号使用。
- **AC-006**：已停用账号用正确凭据登录被拒绝，提示与普通登录失败一致；停用时仍在登录状态的会话在下一次操作时被拒绝并被引导至登录入口；重新启用后可用原凭据登录并按原身份使用系统。
- **AC-007**：已停用的 IT 同事不出现在分派对象中，向其分派被拒绝且工单不变；重新启用后重新出现在分派对象中。
- **AC-008**：被停用账号历史上提交或处理过的工单、沟通记录和处理记录照常保留和显示（含列表、搜索、按处理人筛选、详情和周报表处理量）；停用 IT 同事名下未解决工单仍显示其为处理人，可由其他 IT 同事重新认领或分派。
- **AC-009**：会使系统不再有可用管理员的停用操作（含停用自己）被拒绝并提示原因，账号状态不变；仍有其他可用管理员时，管理员可以停用自己，之后无法再登录。
- **AC-010**：员工和 IT 同事看不到停用 / 启用入口，直接发起这些操作被拒绝且账号状态不变。
- **AC-011**：周报表显示"本周超时解决的工单数量"，其值等于首次已解决时刻在当前自然周内且晚于期望解决时间的工单数；首次已解决时刻不在本周、未晚于期望解决时间、或从未被标记为已解决的工单不计入；无可计入工单时显示 0。
- **AC-012**：周报表 V1 原有四项的口径和结果不变，仍只有管理员可以访问报表。
- **AC-013**：从 V1 升级后，全部账号、类别、工单、沟通记录和处理记录与升级前一致，所有账号为启用状态并可用原凭据登录，各身份按 V1 原权限查看；周报表 V1 四项结果与升级前一致；"设置初始管理员"流程保持不可用。
- **AC-014**：升级后每张 V1 既有工单的期望解决时间按其紧急程度和提交时间以 FR-001 口径计算，并按相同规则显示超时标识和计入周报表第五项。
- **AC-015**：对已升级系统再次执行升级后，全部数据（含升级后新增的工单、记录和账号停用状态）保持不变、无重复记录，既有工单的期望解决时间不变。
- **AC-016**：升级中途中断后再次执行升级，最终数据与一次成功升级的结果相同。

## 测试策略

### 开发者验证

- 对每条 FR 与不变量进行开发者级验证，重点覆盖：三种紧急程度的期望解决时间计算（含跨夜、跨周末、跨月）；期望解决时间在各类操作后不变；超时判定边界（恰好等于期望解决时间、状态在四种之间来回切换）；停用 / 启用对登录、已登录会话、分派对象、分派提交校验的影响；最后一个可用管理员保护（含停用自己、多管理员并存）；非管理员直接发起停用 / 启用被拒；停用账号历史数据在列表、搜索、筛选、详情、报表中的显示；周报表第五项口径与边界（恰好等于、跨周、再次解决、仅关闭、无数据）及 V1 四项不变。
- 升级验证：在含 V1 合成数据的环境上执行升级、重复执行升级、以及在升级中途中断后再次执行升级（AC-016），逐项比对升级前后数据，确认只为既有工单补上期望解决时间。
- 使用合成账号、类别和工单数据，在部署前于开发环境执行；开发者验证结果不能替代 Independent QA 验收。

### Independent QA 验收

- Independent QA 在部署的候选版本上，以黑盒方式（通过网页，以各身份登录）执行 IQA-001～IQA-010。
- 测试素材全部为合成数据（账号、类别、工单文本、提交时间与首次已解决时刻分布）；IQA-002、IQA-008 需要提交时间或首次已解决时刻早于当前时刻、跨越期望解决时间与本周 / 上周边界的合成工单，IQA-009 需要先在 V1 版本中准备的合成数据集，均由测试环境的数据准备方式构造，不需要人工提供真实业务数据。
- 测试环境的管理员账号来源沿用 V1 测试环境的约定；QA 所需的其他员工、IT 同事和管理员账号由可用管理员通过产品功能创建和设置；凭据不得以明文出现在证据中。
- IQA-009、IQA-010 依赖测试环境能够先部署 V1、再升级为 V2 候选版本并再次执行升级；具体执行方式由技术方案决定。V1 线上数据的真实升级结果属于发布阶段的平台证据，不由 Independent QA 以合成数据替代声明。
- 期望值判定：IQA-001、IQA-002、IQA-009 按 BQ-001 人工答案 A（高 4 小时、中 24 小时、低 72 小时，自然时间）计算；IQA-004 按 BQ-003 人工答案 A 判定；IQA-008 按 BQ-002 人工答案 A 计算；IQA-006 按人工审批意见 HT-DLV-20261117-88E4DAE97F6A-0002 判定。

### 总体通过与失败标准

- **通过**：IQA-001～IQA-010 全部通过，且每个场景的必需证据齐全；开发者验证覆盖 AC-016（升级中断后重新执行）并有记录。
- **失败**：任一 IQA 场景的预期结果不满足；或出现停用账号仍能登录或继续使用系统、停用操作导致系统没有可用管理员、非管理员能够停用 / 启用账号、员工看到他人工单；或升级 / 重复升级后任何既有数据缺失、改变或出现重复——以上任一项即判定整体失败，不允许以开发者验证、构建成功、健康检查或页面可打开代替。

## 假设、依赖与范围外边界

**假设**

- **A-001**：V1 规格中的全部产品行为、权限和不变量，除本规格明确新增或修改的部分外，在 V2 中保持不变。
- **A-002**：期望解决时间与超时标识在用户打开或刷新页面时按当时时刻判定，不要求页面在保持打开期间自动刷新标识。
- **A-003**：停用 / 启用操作不要求填写原因或附加说明，也不要求额外审批；停用 / 启用本身不写入工单处理记录。
- **A-004**：已停用账号在工单、沟通记录、处理记录和报表中按原显示姓名显示，不要求额外标注其停用状态。
- **A-005**：管理员仍不查看工单明细（沿用 V1），因此期望解决时间与超时标识只面向员工和 IT 同事显示；周报表通过第五项反映超时解决情况。
- **A-006**：停用 / 启用的目标仅限单个账号，不提供批量停用。

**依赖**

- V1 线上环境及其现有数据可用于直接升级（Intent 业务依赖）。
- 管理员判断并执行具体哪些账号需要停用或重新启用（Intent 业务依赖）。
- 测试环境能够部署 V1 并升级到 V2 候选版本，以执行 IQA-009、IQA-010。

**范围外边界**

超时的邮件 / 即时消息等外部通知、提醒或自动升级；按工作日或节假日日历计算期望解决时间；手工设置或修改期望解决时间、按类别等条件设定不同时限；删除账号、员工自助停用账号、批量停用；改变 V1 周报表四项统计口径；按超时状态搜索或筛选工单；附件、对接公司现有登录系统、自动分派、移动端原生应用等 V1 范围外能力。
