# Independent QA 计划：内部 IT 工单系统 V2

## 范围与依据

- 被测候选：`0b4d4608f1644f204d00bd6222b004b14a5100d9`。地址取 `QA_BASE_URL`（编写计划时为 `AIDH_CANDIDATE_URL`）；依赖为 `ticket-db` 的 `test` 实例（真实 PostgreSQL，没有模拟服务）。
- 依据：`spec.md`「验收场景」IQA-001～IQA-010、「验收标准」AC-001～AC-016；BQ-001、BQ-002、BQ-003 的人工答案 A；人工审批意见 HT-DLV-20261117-88E4DAE97F6A-0002；人工澄清答案 HT-DLV-20261117-88E4DAE97F6A-0005（以及 HT-0006、HT-0007）。`design.md` 只用来定位页面元素（`data-testid`）、路由和「数据库数据契约」，不用来定义预期行为。
- 执行脚本：`runtime/qa-run.sh`。脚本按黑盒方式运行：用 Playwright 驱动 Chromium，以各身份通过 HTTPS 页面操作。回溯时间的合成工单与类别按「数据库数据契约」，以 QA 工作负载身份直连 `ticket-db` 准备（TLS 校验开启，令牌为 Entra 令牌，端口取 `AIDH_DEP_TICKET_DB_PORT`）。
- 账号来源：A1 是业务方提供的初始管理员（`AIDH_SECRET_INITIAL_ADMIN_LOGIN_NAME`、`AIDH_SECRET_INITIAL_ADMIN_PASSWORD`），设置于 V1 时期。其他员工、IT 同事、管理员账号都由 A1 通过「账号管理」页面创建、停用和启用。脚本不以 SQL 写入或修改 `app_user`。合成账号的密码由初始管理员密码经 HMAC 派生，只在内存中使用，不写入任何文件。
- 机密保护：结果、日志、HTML 证据中的机密值统一替换为“«已遮挡»”；截图前把页面中的机密文本替换为遮挡标记。阶段之间保存的状态只包含合成账号的登录名、编号和数据摘要，不包含任何机密值。
- 本次没有需要复测的缺陷，`bugfixResults` 为空数组。
- 分阶段执行：`runtime/qa-phases.json` 声明在 IQA-010 之前重新部署同一候选（`redeployBefore: ["IQA-010"]`），依据是 spec IQA-010 和人工澄清答案 HT-0005 的第 (2) 点。
  - 阶段 1：执行前置、IQA-009、IQA-001～IQA-008，以及 IQA-010 的前置步骤（新增 V2 数据并记录快照，写入 `QA_STATE_DIR`）。
  - 阶段 2：在平台受控重新部署之后执行 IQA-010 的比对和清理。
  - 没有分阶段执行时，按顺序一次执行全部场景，IQA-010 走 spec 中“不执行重新部署”的只读核对路径。

## 执行前置（脚本步骤，不是 IQA 场景）

1. 检查 `QA_DELIVERY_ID`、`QA_CANDIDATE_SHA`、`QA_BASE_URL`、`QA_HEALTH_PATH`、`QA_RESULT_PATH`、`QA_EVIDENCE_DIR`、`AIDH_DEP_TICKET_DB_*`、`AIDH_SECRET_INITIAL_ADMIN_*` 是否提供；分阶段执行时还检查 `QA_STATE_DIR`。只检查是否提供，不输出值。
2. 健康检查：每 10 秒请求一次 `QA_BASE_URL + QA_HEALTH_PATH`，最多重试 5 分钟。
3. 身份校验：`/api/candidate-identity` 返回的 `deliveryId`、`candidateSha` 必须分别等于 `QA_DELIVERY_ID`、`QA_CANDIDATE_SHA`。不一致或不可达时不执行场景，`passed=false`，defects 与 testGaps 都为空。
4. 在工作目录中执行 `npm install`，安装 `playwright`、`pg`、`@azure/identity`。安装失败属于 QA 计划问题，写入 testGaps。
5. A1 登录。如果 A1 因此前某次运行在 IQA-006 中途中断而处于停用状态，就用历次运行的前缀管理员（凭据由派生规则得到）通过页面重新启用 A1。A1 仍不能登录时，说明业务方提供的机密与 `test` 库不一致，写入 testGaps，并注明需由人更正机密或改绑库。
6. 准备合成数据：本次运行使用唯一前缀 `v2q<6位十六进制>-`，不与 V1 基线前缀 `q15-72f2b9041e74-` 相互匹配。
   - A1 通过页面创建员工 E1～E6、D1，IT 同事 T1、T2，以及 IQA-004 专用的 IT 同事 K1、K2、K3（spec 中的 T1、T2、T3）。
   - 插入基础类别，以及 E1 名下的一张工单，供 IQA-009 的越权访问检查使用。
   - 两小时前遗留的同类前缀残留：工单、类别按前缀删除；账号由 A1 通过页面停用。
7. 清理（未分阶段执行时在全部场景之后进行；分阶段执行时在阶段 2 末尾进行）：
   - 按本次前缀删除工单、沟通记录、处理记录和类别。
   - 由 A1 通过页面停用本次运行创建的账号。
   - V1 基线永不清理、永不修改。
8. 结果：向 `QA_RESULT_PATH` 写入唯一一个 JSON 对象，诊断证据写入 `QA_EVIDENCE_DIR`。
   - 每个场景有一份 `IQA-xxx.log`，包含按用户流程排列的检查点、网络请求方法与 URL、状态码和控制台日志；不记录请求体和凭据。
   - 另有截图；失败时还会保存页面 HTML。

## 判定口径

- 场景没有达到已批准的验收行为（包括基线数据缺失或改变）：写入 `defects`，属于产品缺陷。
- 脚本本身没能完成验证（素材无法构造、脚本中断、阶段 1 没有留下快照）：写入 `testGaps`。
- 以下情况属于执行环境问题，`passed=false`，defects 和 testGaps 都为空，在 evidence 中写明诊断：
  - 候选或依赖不可达，或出现 DNS、TLS 失败；
  - V1 基线及其快照整体不存在；
  - 库中存在非 QA 创建的其他可用管理员，使 IQA-006 的前置条件不成立（QA 不处置他人账号）。
- “可用管理员”按 design TD-025 判定：身份为管理员、处于启用状态且有登录凭据。没有凭据、无法登录的历史管理员行不计入，并在证据中记录。
- 共享 `test` 库中可能有其他数据。报表与全局集合的期望值都用同一时刻、按 spec 口径独立编写的 SQL 计算，不复用产品 SQL；在页面读取前后各算一次，任一次完全一致即判一致。
- 超时标识按查看时刻判定。查看时间窗口跨越期望解决时间（±5 秒）时，有标识和无标识两种结果都接受。
