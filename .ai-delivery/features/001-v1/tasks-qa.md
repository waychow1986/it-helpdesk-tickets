## 执行前置（脚本步骤，不是 IQA 场景）

1. 检查平台变量 `QA_DELIVERY_ID`、`QA_CANDIDATE_SHA`、`QA_BASE_URL`、`QA_HEALTH_PATH`、`QA_RESULT_PATH`、`QA_EVIDENCE_DIR`、`AIDH_DEP_TICKET_DB_*` 和 `AIDH_SECRET_INITIAL_ADMIN_*` 是否齐全（只检查是否提供，不输出值）。
2. 健康检查：每 10 秒请求一次 `QA_BASE_URL + QA_HEALTH_PATH`，最多重试 5 分钟。
3. 身份校验：`/api/candidate-identity` 返回的 `deliveryId`、`candidateSha` 必须分别等于 `QA_DELIVERY_ID`、`QA_CANDIDATE_SHA`。不一致或不可达时不执行场景，结果为 `passed=false`，defects 和 testGaps 都为空，按执行环境问题处理。
4. 在工作目录中执行 `npm install`，安装 `playwright`、`pg`、`@azure/identity`、`bcryptjs`。安装失败属于 QA 计划问题，写入 testGaps。
5. 先执行 IQA-016（见清单），由它判定环境所处情形并取得可用的初始管理员。没有可用的初始管理员时（例如情形①中候选未获得有效的设置口令），按 HT-0016 不自备管理员，IQA-001～IQA-014 不执行并如实记录原因。
6. 准备合成数据：本次运行使用唯一前缀 `iq<6位十六进制>-`。初始管理员经「账号管理」页面创建员工 E1、E2，IT 同事 T1、T2、S1、S2 与员工 U1（过程记入 `setup-accounts.log`）；基础类别与工单按数据契约准备。同时清理 2 小时前遗留的同类前缀残留。全部场景结束后，按前缀依次清理 `ticket_event`、`ticket_comment`、`ticket`、`category`、`app_user`（初始管理员除外）。IQA-015 的持久基线（前缀 `q15-72f2b9041e74-`）不在清理范围内，保留给后续迭代核对。
7. 在 IQA-001～IQA-014 改动数据之前，先读取一次周报表，用于 IQA-013 的「无数据」检查。
8. 写出结果：向 `QA_RESULT_PATH` 写入唯一一个 JSON 对象；诊断证据写入 `QA_EVIDENCE_DIR`。每个场景有一份 `IQA-xxx.log`，内容包括检查点、网络请求方法、URL 和状态码（不记录请求体和凭据）、控制台日志；另有截图，失败时还会保存页面 HTML。

## 判定口径

- 场景没有达到已批准的验收行为：写入 `defects`，属于产品缺陷。
- 脚本本身没能完成验证，例如素材无法构造、无法确认前提条件：写入 `testGaps`。
- 候选或依赖不可达，或出现 DNS、TLS 失败，或部署注入的机密不可用（例如候选设置页显示“此部署未提供设置口令”）：`passed=false`，defects 和 testGaps 都为空，在 evidence 中写明诊断。
- 业务方提供的初始管理员机密与 test 库中已设置的管理员不一致（只读核对：该登录名不存在、不是管理员或密码不匹配）：不是产品缺陷，写入 testGaps 并注明需由人更正机密或改绑库。
- 共享 `test` 库中可能有其他数据。页面结果有两种比较方式：一是与本次合成数据的人工期望集合比较；二是与同一时刻按 spec 口径用独立 SQL 计算的全库期望比较。
